1) ARROW FRAMING BUG — FIXED
   v1 failure: server rejected DoPut payload grpc-status=3 "Arrow Flight stream
   decode error ... Type i32 ... unaligned ... 8002". Root cause (confirmed against
   the Rust SDK): our codec stuffed a whole self-contained Arrow IPC *stream* into
   FlightData.data_body and put bogus strings in data_header. The real wire format:
     - schema sent ONCE as the first FlightData's data_header (schema IPC message
       metadata FlatBuffer), no body;
     - each record: data_header = record-batch IPC message metadata FlatBuffer,
       data_body = raw buffers padded to 8-byte alignment;
     - app_metadata = JSON {"offset_id":N}.
   Fix:
     - zerobus_arrow_stubs.cc: use GetSchemaPayload / GetRecordBatchPayload with
       IpcWriteOptions.alignment=8; expose schema_message() + encode() that returns
       a PACKED [4B BE header_len][header][body] blob; decode(~schema_message).
     - lib/core/flight_protocol.ml: create_frame sends the schema (carried in
       table.descriptor) as first data_header; record_frame splits the packed blob
       into data_header/data_body; app_metadata=JSON offset_id; decode_ack parses
       {"ack_up_to_offset":N,...} (the real ack) and {"offset_id":N} and bare int64.
   Live proof: server accepted the stream, sent preliminary {"ack_up_to_offset":-1}
   then {"ack_up_to_offset":4,"ack_up_to_records":5}; 5 Arrow rows persisted.
   Also fixed offline: test_driver_arrow mock now uses the real ack JSON; 3/3 green
   on both switches.

2) FLUSH TIMEOUT — WIRED
   flush_timeout_ms / server_lack_of_ack_timeout_ms were defined but ignored, so a
   non-acking server hung flush forever (v1 symptom before the wsid fix). Now

   Error (Timeout _) if no ack arrives in the window. New offline test
   test_driver/test_flush_timeout_lwt (+ ephemeral_server_noack): flush returns
   Timeout in ~1.5s, 2/2 green.
