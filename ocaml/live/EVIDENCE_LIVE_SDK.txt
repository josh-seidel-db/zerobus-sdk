TWO REAL SDK BUGS THE LIVE TEST CAUGHT (mocks structurally could not)
---------------------------------------------------------------------
1. FIXED — workspace_id derivation (lib/core/config.ml). For an Azure URL
   `adb-984752964297111.11.azuredatabricks.net`, workspace_id_of_url returned the
   WHOLE first label `adb-984752964297111` (old logic: "if the label ends in a
   digit, return the whole label"). That wrong id went into the OAuth `resource`
   audience -> server rejected every stream with grpc-status=16 UNAUTHENTICATED
   "Invalid token audience". Fix: extract the first maximal DIGIT RUN in the label
   -> `984752964297111`. Verified across Azure adb-, GCP numeric, etc. After the
   fix, JSON/Proto/Eio all PASS. (This bug would have broken EVERY Azure adb- user;
   the mocks never exercised OAuth audience so they couldn't see it.)
   Follow-up: add a config unit test for workspace_id_of_url across cloud URL forms.

2. OPEN — Arrow Flight payload framing (zerobus-arrow codec / Flight data_body).
   Server authenticated + accepted the DoPut stream, then rejected the payload with
   grpc-status=3 INVALID_ARGUMENT: "Arrow Flight stream decode error: ... Type `i32`
   ... is unaligned. Error Code: 8002". Our zerobus-arrow.encode emits a full
   self-contained Arrow IPC stream per record placed opaquely in FlightData.data_body;
   the real Zerobus Arrow decoder does not accept that framing/alignment. The mock
   accepted it only because the mock decoded with our OWN symmetric codec. NOT fixed
   here (needs a real design pass on the Arrow-over-Flight wire format vs. the Rust
   SDK's arrow path); tracked as a follow-up. JSON/Proto are the durable-proven paths.
