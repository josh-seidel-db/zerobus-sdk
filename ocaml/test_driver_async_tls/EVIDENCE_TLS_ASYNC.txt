ZEROBUS OCAML — Async live-TLS, IN-TREE TEST (h2 core over tls-async)
=====================================================================
Date: 2026-08-11. Adds the in-tree Async live-TLS test that was the last
"remaining (optional)" item after the Async TLS bypass was solved
(see doc/arch/tls_async_status.md, and spike-async-tls/EVIDENCE_ASYNC_TLS.txt

WHAT THIS IS
------------
The Async counterpart of test_driver_eio/{test_tls_eio.ml, tls_server_eio.ml}:
a self-signed TLS h2 mock (separate process) + a client test that drives the
Zerobus_async public facade over a REAL TLS 1.3 + ALPN-h2 handshake — no live
cloud service needed. Proves handshake + ALPN negotiation of h2 + gRPC framing
over the encrypted flow, AND certificate verification (negative test).

  test_driver_async_tls/
    tls_server_async.ml    self-signed h2 mock; drives H2.Server_connection over
                           a tls-async Reader/Writer duplex (Tls_async.listen);
                           prints "READY <port> <cert-sha256-b64>".
    test_tls_async.ml      pins the mock's cert-fp, drives create -> with_stream
                           (~tls:true) -> ingest 200 -> flush -> close.
    dune                   both (optional) so the dir VANISHES on switches
                           without tls-async (fl414, zbeio) instead of erroring.

async v0.15.0 — see PACKAGING below):
  Testing `phase3-tls-async'.

The 4th case is the important one: a WRONG cert fingerprint makes the TLS
peer-verification fail, stream creation errors, nothing is acked. That proves we
do REAL certificate verification (a pinned cert-fp authenticator), matching the
Eio negative test — not a null authenticator.

HOW CERT PINNING IS THREADED (no live CA needed)
------------------------------------------------
Async's Grpc_transport.connect has no context parameter (unlike Eio's Ctx). So
the pin is a module-level ref on the TLS backend:
  lib/async/tls_connect.real.ml : pinned_cert_fp_sha256_b64 : string option ref
When Some "<sha256-b64>", the real backend authenticates the peer with
  X509.Authenticator.of_string "cert-fp:sha256:<b64>"
instead of Ca_certs (system trust store). Kept a BARE string ref (not an X509/tls
type) so the SHARED tls_connect signature stays tls-free and tls_connect.dummy.ml
still compiles on switches without tls. tls_connect.dummy.ml carries an inert
copy of the ref for signature parity. Re-exported as Zerobus_async.Tls_connect
(in the .mli) for the test; not part of the ergonomic surface.

PACKAGING — why a dedicated switch, and the ONE portability change
------------------------------------------------------------------
There is NO single switch with fl414's EXACT deps AND a working tls-async. The
upstream version triangle:
  - The SDK lib needs h2 = 0.12 (its Body.Writer.flush callback is unit->unit;
    h2 0.13 changed it to [`Written|`Closed]->unit).
  - Pinning h2 0.12 forces tls-async 0.17.0 (the 2.0.x line pulls h2 0.13), which
    in turn pulls async/core v0.15 (fl414 is v0.16), and drags grpc-async down to
    0.1.0 (which has NO Grpc_async.Server module — hence the mock drives
    H2.Server_connection by hand).
So the in-tree test lives on its OWN switch (fl414-tls-intree, a throwaway clone),
exactly like the Eio/spike dirs are switch-specific. The dry-run that proved this
corner exists (h2 stays 0.12): `opam install tls-async --dry-run` on fl414 shows
tls-async.0.17.0 selected with h2 unchanged.

The ONE change to the shipped lib to make this buildable: the Async transport now
uses Clock_ns/Time_ns instead of Time_float (Time_float is async v0.16-only; v0.15
lacks it). Clock_ns/Time_ns exist on BOTH v0.15 and v0.16, so the lib is now
async-version-portable. Verified: lib/async still builds AND the 6 Async mock
tests still pass on fl414 (async v0.16). (This intentionally reverses the old
"do NOT reintroduce Clock_ns" note, which held only under the v0.16-only assumption.)
